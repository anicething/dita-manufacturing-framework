## 1. 概述

### 1.1 问题

在基于 DITA 的文档系统中，单个主题不是独立文档——它们是**成套文档**的组成部分。一份产品手册可能包含 50-500 个主题，横跨多种语言。面临的挑战是：

- 如何知道成套文档是**完整的**（没有遗漏主题）？
- 如何知道成套文档是**一致的**（没有冲突信息，没有断裂引用）？
- 如何知道成套文档是**有效的**（通过质量门禁）？
- 如何跟踪每个组件的**状态**？
- 如何在**不破坏成套结构**的前提下控制变更？

### 1.2 文档成套控制的三大支柱

| 支柱 | 核心问题 | 实现机制 |
|------|---------|---------|
| **成套完整性** | 作为一个整体是否完整且一致？ | DITA Map 验证、关系表、Subject Scheme、跨主题检查 |
| **失效控制** | 每个组件是否处于有效状态？ | Schematron、CI/CD 门禁、pre-commit 钩子、key 解析检查 |
| **状态与变更控制** | 每个主题处于什么状态？谁改了？能否回滚？ | 元数据生命周期、Git 版本控制、变更跟踪、锁定/解锁 |

## 2. 文档成套完整性

### 2.1 DITA Map 作为主控文档

在 DITA 中，**文档成套**由 **DITA Map**（`.ditamap`）定义。Map 是成套文档组成的唯一权威来源。如果一个主题没有被 Map 引用，它就不属于这套文档。

#### Map 完整性检查

| 检查项 | 说明 | 严重级别 | 自动？ |
|--------|------|---------|--------|
| **引用主题存在** | 每个 `<topicref href="...">` 能解析到现有文件 | **阻止** | 是 |
| **无孤立主题** | 产品目录下的每个 `.dita` 文件至少被一个 Map 引用 | 警告 | 是 |
| **无重复主题 ID** | 同个 Map 内没有两个主题共用同一个 `id` | **阻止** | 是 |
| **Map 无循环** | 子 Map 不形成循环包含 | **阻止** | 是 |
| **Key 定义完整** | 文档集中使用的每个 key 都在 key 作用域内有定义 | **阻止** | 是 |
| **无未使用 key 定义** | 定义了但从未引用的 key 生成警告 | 警告 | 是 |

#### 产品 Map 示例

```xml
<map id="mc5000-manual" title="MC-5000 操作手册">
  <topicmeta>
    <othermeta name="doc-collection-type" value="ordered"/>
    <othermeta name="doc-version" content="1.2"/>
    <othermeta name="doc-languages" content="en, zh-CN, de"/>
  </topicmeta>

  <topicref href="../shared/safety-overview.dita" navtitle="安全概述">
    <topicref href="../shared/safety-electrical.dita"/>
    <topicref href="../shared/safety-mechanical.dita"/>
  </topicref>
  <topicref href="../tasks/installation.dita" navtitle="安装">
    <topicref href="../tasks/unpacking.dita"/>
    <topicref href="../tasks/power-connection.dita" collection-type="sequence"/>
  </topicref>
</map>
```

### 2.2 Collection Type 与主题排序

DITA 定义 `collection-type` 属性描述主题之间的关联方式：

| 类型 | 含义 | 验证规则 |
|------|------|---------|
| `unordered` | 可任意顺序阅读 | 无顺序约束 |
| `sequence` | 必须按给定顺序阅读 | 所有主题必须存在，保持线性阅读路径 |
| `choice` | 读者从集合中选择一个 | 输出中至少有一个必须存在 |
| `family` | 主题相关，读者可能需要全部 | 所有主题应完整且一致 |

### 2.3 关系表完整性

关系表（`<reltable>`）定义跨主题链接。关系表断裂会导致输出中导航不完整。

**验证规则：**
- 每个包含 `<topicref>` 的 `<relcell>` 必须解析到有效主题
- 一行中至少两个列应有内容（否则没有需要表达的关系）
- 主题类型应与 `<relcolspec>` 指定的类型匹配

### 2.4 成套级元数据一致性

发布文档集时，所有主题的元数据应保持一致：

| 元数据字段 | 规则 | 执行方式 |
|-----------|------|---------|
| `doc-version` | 同一 Map 内所有主题版本号相同 | Schematron |
| `audience/@type` | 主题必须指定与 Map 目标匹配的读者类型 | Schematron |
| `xml:lang` | 特定语言构建中的所有主题语言必须一致 | DITA-OT |
| `copyright` 年份 | 同次构建中所有主题版权年份一致 | 自动检查 |

### 2.5 Subject Scheme 分类一致性

**完整性规则：** `mc5000-manual` Map 中的每个主题必须带有 `@product="mc5000"` 或从 Map 继承。产品分类不匹配的主题会被标记。

## 3. 失效状态检测与控制

### 3.1 文档失效状态分类

| 状态 | 定义 | 检测方式 | 处理 |
|------|------|---------|------|
| **已断裂** | 有无法解析的引用（conref/keyref/图片） | DITA-OT 链接检查失败 | **阻止发布** |
| **不完整** | 缺少必要的元数据（M1-M7） | Schematron 检查失败 | **阻止发布** |
| **不一致** | 与同一文档集中其他主题矛盾 | 跨主题审计 | 警告 + 人工审查 |
| **过时** | 超过定义的新鲜期未审阅 | 日期检查（`critdates/revised`） | 警告 + 安排重审 |
| **孤立** | 未被任何活跃的 Map 引用 | 文件系统扫描 | 警告 + 归档 |
| **冲突** | 存在未解决的 Git 合并冲突 | Git 状态检查 | **阻止发布** |
| **未批准** | 未通过完整审批流程 | 状态元数据检查 | **阻止发布** |

### 3.2 Schematron 规则集

#### 阻止性规则（必须通过 → 否则无法发布）

```xml
<sch:rule context="*[contains(@class, ' topic/topic ')]">
  <sch:assert test=".//prolog/metadata/author">
    [B1] 主题必须有作者信息（M1）
  </sch:assert>
  <sch:assert test=".//prolog/metadata/audience/@type">
    [B3] 主题必须指定读者类型（M4）
  </sch:assert>
</sch:rule>

<!-- 硬编码变量检测 -->
<sch:rule context="text()">
  <sch:report test="matches(., '示例制造|ECM|MC-\d{4}')">
    [B4] 检测到硬编码变量，请使用 keyref
  </sch:report>
</sch:rule>
```

#### 警告性规则（应通过 → 标记为需审查）

```xml
<sch:rule context="*[contains(@class, ' topic/topic ')]">
  <sch:let name="revised" value=".//prolog/metadata/critdates/revised"/>
  <sch:report test="not($revised) or $revised lt '2025-12-07'">
    [W1] 主题已超过 6 个月未审阅（上次：<sch:value-of select="$revised"/>）
  </sch:report>
</sch:rule>
```

### 3.3 验证门禁矩阵

| 门禁 | 时机 | 检查内容 | 失败后果 |
|------|------|---------|---------|
| **Pre-Commit** | `git commit` 前 | 文件级：XML 格式正确、ID 唯一 | 提交被阻止 |
| **Pre-Push** | `git push` 前 | 主题级：M1-M7 元数据、无硬编码变量 | 推送被阻止 |
| **PR 门禁** | PR 创建时 | 跨主题：key 解析、conref 目标、无孤立 ID | PR 标记为失败 |
| **构建门禁** | 合入 main 后 | Map 级：完整验证 + 关系表 + Subject Scheme | 构建失败 |
| **发布门禁** | 最终发布前 | 输出级：链接检查、无断裂交叉引用 | 发布取消 |
| **发布后** | 发布后 | 回归比较：与上次构建的差异检查 | 生成告警 |

## 4. 文档生命周期与状态控制

### 4.1 文档生命周期状态

每个主题和 Map 都经历明确定义的生命周期：

```
草稿 → 审校中 → 已批准 → 已发布 → 已归档
         ↑ 驳回 |
         └───────┘ (返工)
              ↑ 变更 |
              └──────┘ (修改后重新审校)
```

### 4.2 元数据中的状态跟踪

```xml
<prolog>
  <metadata>
    <othermeta name="doc-lifecycle-status"
               content="draft|in-review|approved|published|archived"/>
    <othermeta name="doc-change-request" content="CR-2026-0042"/>
  </metadata>
</prolog>
```

### 4.3 状态转换规则

| 从 | 到 | 触发条件 | 所需批准 | 自动？ |
|----|-----|---------|---------|-------|
| 草稿 | 审校中 | 作者提交 PR | 无（作者发起） | 否 |
| 审校中 | 草稿 | 审校者要求修改 | 审校者 | 否 |
| 审校中 | 已批准 | 所有审校者批准 | SME + 内容架构师 | 是（审批完成后） |
| 已批准 | 已发布 | 合入 main | CI/CD 流水线通过 | 是 |
| 已发布 | 草稿 | 创建变更请求 | 项目经理批准范围 | 否 |
| 已发布 | 已归档 | 内容被取代 | DGC | 否 |

### 4.4 成套内状态一致性

发布文档集时，所有主题必须处于兼容的状态：

| Map 状态 | 要求的主题状态 | 规则 |
|---------|--------------|------|
| 草稿 | 任意状态 | 无限制——进行中 |
| 审校中 | 草稿或审校中 | 不允许已批准主题（不应重新审校） |
| 已批准 | 全部已批准或已发布 | **阻止**：如有主题是草稿，Map 不能被批准 |
| 已发布 | 全部已发布 | **阻止**：草稿/审校中主题会破坏构建 |
| 已归档 | 全部已归档 | 整套必须一起归档 |

## 5. 跨成套变更控制

### 5.1 变更影响分析

修改共享主题前，作者必须评估影响：

```
变更请求创建
    ↓
影响分析：
  ┌─────────────────────────────────────┐
  │ 哪些 Map 引用了此主题？            │ ← grep -r "href=.*topic-id"
  │ 哪些语言受影响？                    │ ← 语言文件夹检查
  │ 哪些产品受影响？                    │ ← 产品 ditamap 检查
  │ 这是 conref 目标吗？               │ ← grep 查找 conkeyref 引用
  │ 这是 key 定义吗？                   │ ← 检查 framework-keys
  └─────────────────────────────────────┘
    ↓
变更分类 → 见变更权限矩阵 (GOV-003)
    ↓
审批流程 → 执行 → 验证 → 发布
```

#### 自动影响分析脚本

```bash
#!/bin/bash
# impact-analysis.sh — 分析变更影响的脚本
TOPIC_FILE=$1
TOPIC_ID=$(grep -o 'id="[^"]*"' "$TOPIC_FILE" | head -1 | sed 's/id="//;s/"//')

echo "=== 影响分析: $TOPIC_FILE ==="
echo "主题 ID: $TOPIC_ID"
echo "被以下 Map 引用:"
grep -rl "href=.*$(basename $TOPIC_FILE)" products/*/map/*.ditamap 2>/dev/null
echo "被以下 Conref 引用:"
grep -rl "conkeyref.*$TOPIC_ID\|conref.*$TOPIC_FILE" topics/ 2>/dev/null
```

### 5.2 变更类型与版本号规则

| 类型 | 范围 | 版本号变动 | 示例 |
|------|------|-----------|------|
| **补丁** | 单主题、无结构性变更 | 主题次要 (1.2→1.2.1) | 修复拼写、更新截图 |
| **小改** | 单主题、内容变更 | 主题次要 (1.2→1.3) | 更新操作步骤 |
| **大改** | 多主题、结构性变更 | Map 版本 (1→2) | 重新组织章节 |
| **发布** | 整个文档集 | 完整版本 (1.2→2.0) | 产品版本更新 |

### 5.3 并发变更管理

| 场景 | 检测 | 解决 |
|------|------|------|
| 两位作者编辑不同文件 | 无冲突 | Git 干净合并 |
| 两位作者编辑同一文件不同部分 | 无内容冲突 | Git 自动合并 |
| 两位作者编辑同一文件同一部分 | Git 合并冲突 | 手工解决 + 技术内容变更需 SME 重新批准 |
| 两位作者都修改了 conref 目标 | 引用不一致 | CI/CD 检测到断裂 conref；通知两位作者 |
| 一位作者删除了另一个作者依赖的文件 | Map 引用断裂 | CI/CD 失败；需恢复文件或更新 Map |

## 6. 自动化验证流水线

### 6.1 完整流水线流程

```
[作者提交]
    ↓
┌─────────────────────────────────────┐
│ 阶段 1：Pre-Commit 钩子（本地，<1秒）│
│   • XML 格式正确性                   │
│   • 文件内 ID 唯一性                  │
│   • DTD/Schema 引用有效              │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 阶段 2：Pre-Push 钩子（本地，<5秒）  │
│   • M1-M7 元数据完整                  │
│   • 无硬编码公司/产品名称             │
│   • 主题 ID 符合命名规范              │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 阶段 3：PR 验证（CI，<1分钟）        │
│   • Key 解析 — 所有 keyref 可解析     │
│   • Conref 解析 — 所有 conref 可解析  │
│   • 无孤立 ID — PR 内无重复 ID       │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 阶段 4：构建验证（CI，<5分钟）       │
│   • 完整 DITA-OT 构建（所有配置）     │
│   • 完整 Schematron 验证              │
│   • 内容新鲜度检查（过时警告）        │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 阶段 5：发布门禁（CI，<10分钟）      │
│   • 所有语言完整构建                  │
│   • 输出链接检查                      │
│   • 跨语言一致性检查                  │
│   • 与上次构建的回归差异比较          │
└─────────────────────────────────────┘
```

## 7. 冲突解决与恢复

### 7.1 Git 合并冲突解决

```
1. 检测：Git 标记冲突文件
   ↓
2. 通知：作者 + CoE 负责人收到冲突通知
   ↓
3. 评估：哪些变更冲突？（结构性 vs. 编辑性）
   ↓
4. 解决：
   - 仅编辑性变更 → 取最新版本
   - 技术性变更 → SME 重新批准
   - 结构性变更（ID/Map 修改）→ 内容架构师审查
   ↓
5. 验证：CI/CD 重新运行验证
   ↓
6. 合并：仅通过绿灯构建后
```

### 7.2 回滚流程

```bash
# 1. 定位错误提交
git log --oneline -10

# 2. 创建回退提交（非破坏性 reset）
git revert <bad-commit-hash>

# 3. 推送回退
git push origin main

# 4. CI/CD 自动使用回退内容重新构建
# 5. 通知利益相关方回退完成
# 6. 创建事故报告
```

### 7.3 恢复时间目标

| 故障类型 | 恢复时间 | 流程 |
|---------|---------|------|
| conref/keyref 断裂 | 4 小时 | 回退提交或修复引用 |
| 元数据验证失败 | 2 小时 | 修复元数据或调整 Schematron 规则 |
| 构建流水线失败 | 4 小时 | 参见 SEV-2 流程 |
| 已发布的安全错误 | 1 小时 | 参见 SEV-1 流程 |
| 仓库损坏 | 24 小时 | 从备份恢复 |

## 8. 治理与审计

### 8.1 变更日志要求

已发布的文档集的每次变更都必须可追溯：

| 要求 | 信息来源 | 审计频率 |
|------|---------|---------|
| 谁做了变更？ | Git author + `prolog/author` | 每次提交 |
| 何时做的？ | Git timestamp + `critdates/revised` | 每次提交 |
| 为什么做？ | Git commit message + PR 描述 | 每次 PR |
| 谁批准的？ | PR 审校人列表 + `othermeta` | 每次合并 |
| 改了哪些文件？ | PR 中的文件列表 | 每次 PR |

### 8.2 定期审计

| 审计类型 | 频率 | 范围 | 执行者 |
|---------|------|------|--------|
| 主题新鲜度扫描 | 每月 | 所有主题：最后审阅日期对比当前日期 | 自动 |
| 孤立主题扫描 | 每月 | 未被任何活跃 Map 引用的主题 | 自动 |
| Key 使用审计 | 每季 | 已定义 vs. 已使用的 key；识别废弃 key 定义 | 自动 |
| 元数据合规 | 每季 | 所有活跃主题的 M1-M7 完整性 | 自动 |
| 完整集回归 | 每季 | 已发布归档 vs. 当前构建的意外差异 | 自动 |
