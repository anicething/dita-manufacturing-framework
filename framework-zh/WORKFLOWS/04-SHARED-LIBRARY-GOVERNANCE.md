## 1. 目的与范围

### 1.1 目的

共享库（`references/` 目录及所有 conref 目标主题）是驱动 DITA 内容复用价值的核心资产。没有治理，共享库将退化为：

- **孤立内容** — 无人知晓或使用的主题
- **过期内容** — 过时信息静默传播到所有产品
- **断裂引用** — 未检查所有依赖项即删除了 conref 目标
- **重复库条目** — 因作者找不到现有条目而创建的近似重复主题

本文档建立了保持共享库健康、可发现和可靠的治理流程。

### 1.2 范围

本流程适用于：

| 范围内 | 范围外 |
|--------|--------|
| `references/` 目录中的主题 | 各产品主题目录 |
| Conref 目标主题（带 `@id` 目标的 `.dita` 文件） | 各产品 ditamap |
| 变量定义文件（`.ditamap` 键定义） | 各产品变量覆盖 |
| 共享 ditamap（跨产品地图） | 个人工作区文件 |
| 术语表条目 | 模板文件 |
| 法律免责声明主题 | — |

### 1.3 设计原则

1. **共享一次，处处复用** — 两个或以上产品需要的内容应放入共享库
2. **稳定性即服务** — 作者必须能信任库内容不会破坏他们的主题
3. **变更必须通知** — 每次库修改必须告知所有受影响作者
4. **管理员是守门员** — 指定的"复用管理员"角色拥有共享库
5. **可发现性设计** — 清晰的命名、元数据和索引便于搜索

## 2. 共享库结构

### 2.1 目录布局

```
references/
├── framework-keys.ditamap         # 中心键定义（公司、产品、标准）
├── variables.ent                  # 遗留 XML 实体变量
├── en/                            # 英文共享内容
│   ├── company-variables.dita     # 公司名称、地址、联系方式
│   ├── legal-statements.dita      # 版权、免责声明、商标
│   ├── safety-common.dita         # 共享安全警告
│   ├── procedures-common.dita     # 跨产品流程
│   ├── specifications-common.dita # 共享规格表
│   └── glossary/                  # 术语表条目
├── zh-CN/                         # 中文共享内容
│   ├── company-variables.dita
│   ├── legal-statements.dita
│   ├── safety-common.dita
│   ├── procedures-common.dita
│   ├── specifications-common.dita
│   └── glossary/
├── de/                            # 德语（Tier-1）
├── fr/                            # 法语（Tier-1）
└── es/                            # 西班牙语（Tier-1）
```

### 2.2 命名约定

| 元素 | 约定 | 示例 |
|------|------|------|
| 库主题文件 | `{领域}-{用途}.dita` | `safety-electrical.dita` |
| Conref 目标 ID | `{主题简称}-{目标名称}` | `safety-electrical-lockout` |
| 键名称 | `{类别}-{具体名称}` | `company-name`、`standard-iso9001` |
| 术语条目 | `glossentry-{术语}` | `glossentry-torque` |
| 变量文件 | `{语言}-{领域}-variables.dita` | `en-company-variables.dita` |

### 2.3 库主题必需元数据

每个共享库主题**必须**包含完整的 M1-M7 元数据：

```xml
<prolog>
  <metadata>
    <author>张明</author>
    <publisher>文档治理委员会</publisher>
    <critdates>
      <created date="2026-01-15"/>
      <revised modified="2026-06-01"/>
    </critdates>
    <audience type="administrator" job="maintenance" level="expert"/>
    <category>安全</category>
    <prodinfo>
      <prodname>共享库</prodname>
      <vrmlist>
        <vrm version="1.0" release="0" modification="3"/>
      </vrmlist>
    </prodinfo>
  </metadata>
</prolog>
```

## 3. 角色与职责

### 3.1 共享库角色

| 角色 | 担任者 | 职责 |
|------|--------|------|
| **复用管理员** | 高级技术写作人员 | 所有库变更的守门员，质量负责人 |
| **内容架构师** | 文档架构师 | 设计库结构、命名规范、元数据模式 |
| **库贡献者** | 所有技术写作人员 | 提议添加内容、报告问题、维护自身条目 |
| **变更评审员** | 同级写作人员 + SME | 评审提议变更的正确性和影响 |
| **DGC（治理委员会）** | 文档治理委员会 | 批准结构性变更、解决争议、制定政策 |

### 3.2 复用管理员 — 详细职责

复用管理员是库健康最关键的角色：

**每周：**
- 审查并合并或拒绝待处理的库变更请求
- 验证所有 conref 目标至少被一个主题引用
- 回复作者团队提出的库相关问题

**每月：**
- 运行复用扫描器并向 DGC 报告指标
- 识别孤立或过期的库内容
- 主持月度库评审会议

**每季度：**
- 进行全面库审计（内容准确度、元数据完整性）
- 发布库健康报告
- 推荐库结构改进

**临时：**
- 调查并修复断裂的 conref 引用
- 协调紧急库变更（如安全内容更新）
- 培训新作者使用共享库

## 4. 共享库内容生命周期

### 4.1 生命周期状态

```
[草稿] → [评审中] → [已批准] → [已发布] → [已弃用] → [已归档]
                              ↘ [已拒绝] ↗
```

| 状态 | 说明 | 谁可转换 |
|------|------|---------|
| **草稿** | 提议的库内容，尚未评审 | 任何库贡献者 |
| **评审中** | 正在积极评审 | 管理员（从草稿移入） |
| **已批准** | 已通过评审，等待下个发布周期 | 变更评审员 |
| **已发布** | 在共享库中生效，所有作者可用 | 管理员 |
| **已弃用** | 仍可用但标记为待移除 | DGC |
| **已归档** | 已从库中移除，仅保留在 git 历史中 | 管理员 |
| **已拒绝** | 评审认为不适合入库 | 变更评审员 |

### 4.2 状态转换规则

| 从 | 到 | 要求 | 通知 |
|----|----|------|------|
| 草稿 | 评审中 | 完整元数据 + 2 个使用场景 | 通知贡献者 |
| 评审中 | 已批准 | 2 个同行批准 + SME 签署 | 通知评审员 |
| 已批准 | 已发布 | 管理员批准 | 通知所有作者 |
| 已发布 | 已弃用 | DGC 投票 + 影响分析 | 通知所有作者和消费者 |
| 已弃用 | 已归档 | 90 天通知期 + 0 活动引用 | 所有团队确认 |
| 评审中 | 已拒绝 | 任何评审员提供书面理由 | 通知贡献者 |

## 5. 向共享库添加新内容

### 5.1 资格标准

满足**任何**以下条件的内容符合共享库资格：

- [ ] 被 2+ 个产品或产品系列使用
- [ ] 合规/监管要求（安全、法律）
- [ ] 公司级变量定义（名称、地址、标准）
- [ ] 带有正式定义的术语表条目
- [ ] 跨 2+ 个产品完全相同的流程

### 5.2 提交流程

**第 1 步：提案**（作者）
1. 识别符合共享条件的内容
2. 在 `references/` 中的特性分支上创建草稿主题
3. 包含完整的 M1-M7 元数据
4. 创建标注 `library-add` 的拉取请求

**第 2 步：资格检查**（管理员 — 1 个工作日）
1. 验证资格标准是否满足
2. 检查命名约定符合性
3. 确认不存在重复内容
4. 分配变更评审员

**第 3 步：同行评审**（2 名评审员 — 2 个工作日）
1. 审查技术准确性
2. 验证 conref 目标已正确标记 `@id`
3. 确认主题遵循风格指南
4. 测试键定义能否正确解析

**第 4 步：管理员批准**（管理员 — 1 个工作日）
1. 最终质量检查
2. 合并到主分支
3. 向所有作者宣布新的库内容

### 5.3 库添加的 PR 模板

```markdown
## 库添加提案

**主题：** [简要标题]
**文件：** references/[语言]/[文件名].dita

### 资格
- [ ] 被 2+ 个产品使用 — 列出：[列表]
- [ ] 合规/监管要求
- [ ] 公司级变量
- [ ] 术语表条目
- [ ] 跨产品流程

### 元数据
- 作者：[姓名]
- 读者对象：[类型/岗位/级别]
- 类别：[选择一项]

### 影响
- 受影响产品：[全部 / 具体]
- 新增键定义：[键名称]

### 评审员
- SME：[姓名]
- 同行：[姓名]
```

## 6. 修改现有共享内容

### 6.1 变更分类

| 类别 | 定义 | 示例 | 紧急程度 |
|------|------|------|---------|
| **补丁** | 无内容变更，仅修复 | 拼写修正，格式修复 | 低 |
| **次要** | 不影响引用的内容变更 | 更新步骤，新增示例 | 中 |
| **重大** | 可能影响引用主题的内容变更 | 重组章节，修改值 | 高 |
| **破坏性** | 必然影响引用主题的内容变更 | 删除 conref 目标，修改键定义 | 关键 |

### 6.2 修改工作流

```
补丁：   作者修复 → 管理员评审 → 合并 → 通知
次要：   作者建分支 → 同行评审 → 管理员 → 合并 → 通知
重大：   作者建分支 → 影响分析 → SME 评审 → 管理员 → 合并 → 通知
破坏性： DGC 批准 → 影响分析 → 2 周通知 → 迁移计划 → 执行 → 验证
```

### 6.3 影响分析要求

对于**重大**和**破坏性**变更，作者必须提供：

```markdown
## 影响分析

### 内容影响
- 引用此库主题的文件：[数量和列表]
- 引用此库主题的地图：[数量和列表]
- 受影响的 Conref 目标：[@id 值列表]

### 引用影响
- 使用 conref 引用此文件的主题：[数量]
- 受影响的键引用：[数量]
- 受影响的术语表引用：[数量]

### 迁移计划
1. [逐步更新计划]
2. 预估工作量：[小时]
3. 回滚方案：[说明]
```

### 6.4 修改内容的版本追踪

每个库主题应在元数据中追踪其版本：

```xml
<critdates>
  <created date="2026-01-15"/>
  <revised modified="2026-06-01">根据 ISO 13849-1:2025 更新电气规格</revised>
</critdates>
```

## 7. 弃用与移除共享内容

### 7.1 弃用工作流

1. **提案**：DGC 成员提出弃用建议及理由
2. **影响评估**：管理员识别所有引用主题
3. **迁移**：引用主题的作者更新内容
4. **通知期**：已发布内容有 90 天弃用通知期
5. **移除引用**：移除前必须替换所有引用
6. **归档**：内容移至 git 历史（不从 git 删除）

### 7.2 弃用通知模板

```markdown
## 弃用通知

**主题：** [文件名.dita]
**弃用日期：** [日期]
**计划移除：** [日期 + 90 天]
**原因：** [理由]
**替代方案：** [替代主题或键]

### 需要采取的行动
如果您的主题引用此内容，请在移除日期前更新。

### 剩余引用
- [数量] 个直接 conref 引用
- [数量] 个地图引用
- [数量] 个键引用

### 联系方式
如有疑问或需要迁移协助，请联系[管理员姓名]。
```

### 7.3 紧急移除

仅在以下情况下，内容可立即移除（无通知期）：

| 情况 | 示例 | 处理方式 |
|------|------|---------|
| **安全错误** | 错误的安全流程 | 移除 + 发布安全公告 |
| **法律违规** | 受版权保护内容、监管违规 | 移除 + 通知法务部 |
| **安全问题** | 泄露凭证、内部数据 | 移除 + 安全审计 |

紧急移除需要 DGC 主席批准，并且必须在 24 小时内进行事件报告。

## 8. 变更通知规则

### 8.1 通知矩阵

| 变更类别 | 通知方式 | 受众 | 提前时间 |
|---------|---------|------|---------|
| 补丁 | PR 评论 | 管理员 + 作者 | 即时 |

## 9. Conref 目标稳定性

### 9.1 黄金法则

> **在确认零活动引用之前，切勿删除或重命名 conref 目标 `@id`。**

Conref 目标的 `@id` 是一个契约。一旦发布，组织内的所有作者都可能引用它。破坏该契约会静默地将错误传播到所有产品。

### 9.2 Conref 目标变更规则

| 操作 | 允许？ | 条件 |
|------|--------|------|
| 新增 `@id` | ✅ 始终允许 | 无影响 |
| 修改现有 `@id` 的内容 | ✅ 谨慎操作 | 不得在未通知的情况下改变语义含义 |
| 重命名现有 `@id` | ❌ 禁止 | 添加新 ID，弃用旧 ID |
| 删除现有 `@id` | ❌ 禁止 | 先弃用，90 天后确认 0 引用 |
| 更改 `@id` 值 | ❌ 禁止 | 与重命名相同 |

### 9.3 Conref 目标验证脚本

```bash
#!/bin/bash
echo "=== Conref 目标引用检查 ==="

find references/ -name "*.dita" | while read lib_topic; do
    grep -oP 'id="[^"]*"' "$lib_topic" | sed 's/id="//;s/"//' | while read target_id; do
        ref_count=$(grep -r "conref=.*#.*/$target_id\"" --include="*.dita" . \
            -not -path "*/output/*" -not -path "*/templates/*" | wc -l)
        
        if [ "$ref_count" -eq 0 ]; then
            echo "⚠️  未引用：$target_id 位于 $lib_topic"
        else
            echo "✅  正常（$ref_count 次引用）：$target_id"
        fi
    done
done
```

## 10. 库版本策略

### 10.1 版本号方案

库主题使用语义化版本：`主版本.次版本.补丁`

| 组件 | 何时递增 | 示例 |
|------|---------|------|
| **主版本** | 破坏性变更（删除 conref 目标、更改键定义） | 1.0.0 → 2.0.0 |
| **次版本** | 新增或修改内容（新增章节、更新值） | 1.0.0 → 1.1.0 |
| **补丁** | 仅修复（拼写、格式） | 1.0.0 → 1.0.1 |

### 10.2 版本追踪

在两个位置追踪库主题版本：

1. **文件元数据**（prolog 中的 `<vrmlist>`）：
```xml
<vrmlist>
  <vrm version="1" release="2" modification="3"/>
</vrmlist>
<!-- 代表版本 1.2.3 -->
```

2. **变更日志**（`references/CHANGELOG.md`）：
```markdown
# 共享库变更日志

## 2026-06-07
### safety-common.dita v1.1.0
- 新增电气锁定流程目标（`#safety-electrical-lockout`）
- 根据 ISO 13849-1:2025 更新 PPE 要求

### company-variables.dita v1.0.2
- 修正公司地址中的拼写错误（邮政编码）
```

### 10.3 版本兼容性

| 库版本 | 兼容范围 | 说明 |
|--------|---------|------|
| 相同主版本 | 所有消费者 | 安全更新 |
| 新主版本 | 消费者需更新引用 | 破坏性变更 |
| 已弃用 | 消费者应迁移 | 不再维护 |

## 11. 评审节奏与质量

### 11.1 评审计划

| 评审类型 | 频率 | 参与人 | 重点 |
|---------|------|--------|------|
| **每周分类** | 每周 | 管理员 | 新提交、待定评审 |
| **月度健康检查** | 每月 | 管理员 + 内容架构师 | 引用计数、孤立检测 |
| **季度审计** | 每季度 | 管理员 + DGC | 全内容审计、元数据完整性 |
| **年度结构评审** | 每年 | DGC + 内容架构师 | 库结构、命名、效率 |

### 11.2 库内容质量标准

| 标准 | 要求 | 衡量方式 |
|------|------|---------|
| 元数据完整性 | M1-M7 全部存在 | Schematron 检查 |
| Conref 目标覆盖率 | 每个目标被 1+ 主题引用 | 每周扫描 |
| 重复检测 | 无近似重复内容 | 季度审计 |
| 新鲜度 | 12 个月内无人评审的内容不超过 | 季度审计 |
| 跨语言一致性 | Tier-1 所有语言版本存在 | 每月检查 |
| 命名合规 | 遵循命名约定 | PR 评审 |

### 11.3 库健康评分

每季度计算库健康评分：

```
健康评分 = (R + C + D + F + L + N) / 6 × 100

R = 有 1+ 引用的主题 / 库主题总数
C = 元数据完整的主题 / 库主题总数
D = 唯一内容主题 / 库主题总数（1 - 重复率）
F = 12 个月内评审的主题 / 库主题总数
L = 完整覆盖的语言数 / Tier-1 语言总数
N = 遵循命名约定的主题 / 库主题总数
```

**目标健康评分：> 85%**

## 12. 冲突解决

### 12.1 常见冲突

| 冲突 | 示例 | 解决流程 |
|------|------|---------|
| **所有权争议** | 两个团队声称对某个库主题拥有所有权 | 上报 DGC 决策 |
| **内容分歧** | SME 对流程步骤意见不一致 | 主持会议，记录双方意见 |
| **命名冲突** | 两个提议文件同名 | 管理员决定，必要时添加别名 |
| **优先级冲突** | 两个团队同时需要冲突的变更 | DGC 按发布计划确定优先级 |
| **质量争议** | 作者对库提交被拒绝有异议 | 管理员 + 内容架构师终审 |

### 12.2 升级路径

```
1. 作者 ↔ 管理员（讨论解决）
2. 管理员 ↔ 内容架构师（如未解决）
3. DGC 主席（如第 2 步仍未达成一致）
4. DGC 投票（最终、具有约束力）
```

## 13. 治理规则汇总

### 13.1 禁止规则

| 规则 ID | 规则 | Schematron | 违规处理 |
|---------|------|-----------|---------|
| **SL-B1** | 不得 conref 到已弃用内容 | ✅ | 阻止 PR |
| **SL-B2** | 所有库主题必须有完整的 M1-M7 元数据 | ✅ | 阻止 PR |
| **SL-B3** | 未经 0 引用验证不得删除 conref 目标 | 手动 | 阻止合并 |
| **SL-B4** | 新库内容必须有 2+ 产品使用案例 | 手动 | 阻止 PR |
| **SL-B5** | 重大/破坏性变更需要影响分析 | 手动 | 阻止 PR |
| **SL-B6** | 破坏性变更需要 2 周通知 | 手动 | 阻止合并 |

### 13.2 警告规则

| 规则 ID | 规则 | 处理方式 |
|---------|------|---------|
| **SL-W1** | 库主题 90 天以上无引用 | 标记为待弃用 |
| **SL-W2** | 库主题 12 个月以上未评审 | 标记为待审计 |
| **SL-W3** | 库主题缺少一个或多个 Tier-1 语言版本 | 标记为待翻译 |
| **SL-W4** | Conref 目标被 0 个主题引用 | 标记为待移除 |
| **SL-W5** | 库主题超过 500 字（可能过大） | 标记为待审查 |
