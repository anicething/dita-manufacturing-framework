# 第一部分
## DITA 卓越中心 (CoE)

---

## 什么是 DITA 卓越中心

DITA 卓越中心 (Center of Excellence, CoE) 是**负责企业级 DITA 战略、标准制定、工具支持和培训赋能的专职团队**。

```
            ┌──────────────────────────────┐
            │      DITA 卓越中心 (CoE)       │
            ├──────────┬─────────┬─────────┤
            │ 标准制定  │ 工具平台 │ 培训赋能 │
            │ · 信息模型│ · DITA-OT│ · 入门课 │
            │ · 模板库  │ · CCMS   │ · 进阶课 │
            │ · 样式表  │ · CI/CD  │ · 认证   │
            └──────────┴─────────┴─────────┘
```

CoE 不是"管理部门"，而是**服务与赋能团队**。

---

## 为什么制造业需要 CoE

| 痛点 | 无 CoE 的表现 | CoE 解决方案 |
|------|-------------|-------------|
| **标准不统一** | 每个产品线自行定义 DITA 结构 | 统一信息模型与模板库 |
| **工具碎片化** | 团队各自安装不同版本 DITA-OT | 中央管理工具链与插件 |
| **重复造轮子** | 相同专用化被多次独立开发 | CoE 统一开发与维护 |
| **质量参差不齐** | 审查标准不一，隐患难发现 | 统一质量门禁与审查清单 |
| **知识断层** | 核心成员离职导致经验流失 | 文档化知识与标准化培训 |

对于示例制造而言，CoE 是**投资回报率最高的组织变革**。

## CoE 组织架构建议

示例制造 DITA CoE 建议编制（初期 4-5 人）：

```
DITA CoE 负责人 (1人)
  ├── 信息架构师 (1人)
  │     └── 负责: DITA 专用化、信息模型、元数据策略
  ├── 工具与自动化工程师 (1人)
  │     └── 负责: DITA-OT、CI/CD、CCMS、插件开发
  ├── 内容策略与质量专员 (1人)
  │     └── 负责: 模板、风格指南、质量审计、KPI
  └── 培训与推广专员 (1人, 可兼职)
        └── 负责: 培训课程、文档文化推广、新人入职
```

初期可由现有技术写作团队兼任，逐步专职化。

## 核心团队角色定义

| 角色 | 核心职责 | 需要技能 |
|------|---------|---------|
| **信息架构师** | DITA 专用化设计、信息模型维护、元数据策略 | XML Schema、DTD、制造业领域知识 |
| **工具工程师** | DITA-OT 配置、CI/CD、插件开发、CCMS 管理 | Java/XSLT、DevOps、CI/CD |
| **内容策略师** | 模板设计、风格指南、质量审计、内容分析 | 技术写作、数据分析、质量体系 |
| **培训专员** | 课程开发、内部培训、认证管理、文档文化 | 教学设计、DITA 专业知识、沟通 |
| **技术写作者** | 日常内容创作、主题编写、审校 | DITA XML、制造业知识、写作技巧 |
| **主题专家(SME)** | 技术内容审核、准确性验证 | 工程专业知识、产品深度认知 |

<!-- _class: keypoint -->

## 关键要点：角色与 RACI

- RACI 避免"人人负责 = 无人负责"
- 每个关键活动必须有且只有一个 **A** (责任人)
- 信息架构师管控信息模型变更
- 工具工程师是 CI/CD 的唯一责任人
- SME 参与技术审核但不负责文档语法

# 第三部分
## 内容所有权模型

---

## 三种内容所有权模型

| 模型 | 描述 | 适用场景 |
|------|------|---------|
| **集中式** | CoE 拥有全部内容，写作者向 CoE 汇报 | 小型组织，产品线少 |
| **联邦式** | CoE 制定标准，各业务部门自有写作者 | 中型组织，多产品线 |
| **混合式** | 核心/共享内容归 CoE，产品特定归部门 | 大型组织，产品差异大 |

示例推荐：**混合式模型**

---

## 示例混合式所有权模型

│                   CoE 管辖范围                        │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────┐   │
│  │ 共享安全库 │  │ 通用操作库 │  │ 术语表/术语库     │   │
│  │ (CoE 拥有) │  │ (CoE 拥有) │  │ (CoE 拥有)       │   │
│  └──────────┘  └──────────┘  └──────────────────┘   │
│  ┌──────────────────────────────────────────────┐    │
│  │         DITA 框架 (信息模型、模板、样式表)      │    │

## 内容审核与审批工作流

```
草稿 → 同行审核 → SME 技术审核 → 合规审核 → 发布
 │         │            │            │         │
 │    ┌────┴────┐  ┌────┴────┐  ┌───┴────┐   │
 │    │ 语法检查 │  │ 准确性   │  │ 法规    │   │
 │    │ 风格检查 │  │ 完整性   │  │ 安全    │   │
 │    │ 复用检查 │  │ 安全性   │  │ 法律    │   │
 │    └─────────┘  └─────────┘  └────────┘   │
 │                                            │
 └────────────────────────────────────────────┘
              状态在 CCMS 中追踪
```

每次审核不通过 → 退回草稿，附审核意见。

---

## 内容版本控制策略

| 内容类型 | 版本策略 | 示例 |
|---------|---------|------|
| **安全信息** | 修改 → 主版本升级 (v2.0 → v3.0) | 安全警告变更 |
| **操作步骤** | 内容变更 → 次版本升级 (v2.1 → v2.2) | 新增一个步骤 |
| **规格参数** | 数据变更 → 补丁版本 (v2.1.0 → v2.1.1) | 扭矩值纠正 |
| **翻译内容** | 源语言变更 → 翻译状态重置 | 英文更新，西语标记"待译" |

工具实现：Git 版本号 + CCMS 元数据双重追踪。

## 练习二：所有权冲突解决

**场景**：CNC 部门想在共享安全库中修改一条安全警告，因为他们认为原表述不够精确。"紧急停止后必须等待主轴完全停止" → 他们想改为"紧急停止后必须等待主轴确认完全停止（约 15 秒）"。

**问题**：
1. 谁有权修改共享安全库的内容？
2. 如果 CNC 部门直接修改了原文，会产生什么后果？
3. 正确的修改流程是什么？
4. 翻译过的语言版本如何同步更新？

---

<!-- _class: keypoint -->

## 关键要点：内容所有权

- 示例采用混合式模型：共享内容归 CoE，产品特定内容归各部门
- 共享内容的修改必须经过 CoE 审批
- 每次修改都需要版本号更新
- 翻译版本标记"待译"后由翻译供应商同步
- 审核流程：草稿 → 同行 → SME → 合规 → 发布
